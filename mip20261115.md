## 1. Central argument

The article argues that a personal knowledge system should do more than retain
documents for later search. When a source arrives, an agent should extract its
useful information, reconcile it with existing material, update persistent
summaries, connect related concepts, and identify disagreements. Later work can
reuse that synthesis instead of repeatedly reconstructing it from raw sources.

The compiler analogy describes this transformation:

```text
Selected sources
    -> extraction and comparison
    -> persistent, linked knowledge
    -> answers, decisions, and deliverables

New evidence and reviewed feedback
    -> revisions to the persistent knowledge
```

The persistent knowledge base is the accumulating asset. The model is the
processor and maintainer; saving pages does not itself train its weights.

## 3. The article's proposed architecture

### Raw inputs

The proposed `raw/` directory receives articles, notes, papers, transcripts, and
other source material. The author treats it as input awaiting processing, rather
than the finished knowledge base.

The useful distinction is between source material and derived understanding.
Sources must remain available for verification, corrections, and information
that a summary omitted. The article's stronger suggestion that raw material is
never an answer should not prevent direct source consultation.

### Maintained knowledge

The proposed `wiki/` directory contains model-maintained concept pages, source
summaries, connections, and reconciled explanations. An incoming source may
affect several existing pages. The human reads and reviews this layer while the
agent performs much of the drafting and organisation.

The article describes one source touching ten to fifteen pages. This is an
example of possible integration, not a required amount of work. Creating links
or pages without a useful relationship would increase maintenance burden.

### Outputs

The proposed `output/` directory holds deliverables generated using accumulated
knowledge: briefs, analyses, plans, and other work products. The intended benefit
is consistency with previously processed material.

An output still needs evidence and current reasoning. Generating a deliverable
does not automatically make its conclusions established knowledge.

### Standing instructions and personal context

The article proposes a living root instruction document containing the user's
background, communication preferences, goals, strengths, weaknesses, previous
attempts, and projects. It expects this context to be available across sessions.

Two responsibilities should be separated when applying the idea:

1. Owner-controlled instructions describe the agent's role, rules, and workflow.
2. Evidence-backed personal and project knowledge records what is known, when it
   was observed, and how it was supported.

An inferred preference or a statement in an imported document must not silently
become an authoritative instruction. Detailed knowledge can be retrieved when
needed instead of loading the entire collection into every session.

## 4. Operating workflows described in the article

### Source ingestion

The article's ingestion prompt asks the agent to:

1. Read a newly added source.
2. Extract its main concepts and claims.
3. Write appropriate concept articles.
4. Link them to related existing pages.
5. Identify contradictions with existing material.
6. Summarise the changes in three sentences.

For Moon, an ingestion design should first search for existing concepts and
claims. Extending a suitable record is preferable to creating near-duplicates.
Extracted claims should retain their source attribution, scope, qualifications,
and uncertainty. A source reporting a claim is evidence that the claim was made,
not necessarily proof that it is true.

### Personal-context setup

The article suggests interviewing the user one question at a time about their
role, annual goals, preferred communication, strengths, weaknesses, and projects.
The resulting context is saved for future sessions.

The transferable idea is deliberate context collection. User statements and
agent interpretations should remain distinguishable. Context needs correction,
scope, and freshness mechanisms rather than becoming a permanent biography.

### Project setup

The suggested project structure is:

```text
project/
    Inputs/
    Process/
    Outputs/
    Feedback/
    project instructions
```

Project instructions describe its purpose, single goal, completion criteria, and
the agent's role. The folders are organisational suggestions. They do not require
Moon to introduce another canonical storage system.

### Daily maintenance and change brief

The article proposes a daily task that processes new inputs, links related
notes, flags possible staleness, checks recent additions for contradictions, and
reports what changed, what was linked, what was flagged, and what deserves human
attention.

Its two-week inactivity rule is a review reminder, not evidence that a claim has
expired. Freshness should depend on the subject, validity period, supporting
evidence, and actual changes. Stable facts and temporary service status need
different policies.

### Querying and preserving useful work

The article emphasises generating work from the maintained knowledge layer.
Karpathy's original proposal also describes searching relevant wiki pages,
answering with citations, and saving useful query-time analyses back into the
wiki. It adds an explicit maintenance operation and separate index and log files.

Saving an answer should be selective. Repetition of an existing generated claim
must not count as independent confirmation, and a new inference should remain
labelled as an inference until it has appropriate support.

## 5. Benefits and limitations claimed by the article

### Expected benefits

- Less context loss between sessions.
- Reuse of prior analysis and connections across sources.
- Less manual filing, cross-referencing, and routine updating.
- More accumulated value as the knowledge base becomes useful and well connected.
- Better visibility through a short maintenance brief.

The article describes improvements after one month, three months, six months,
and one year. These are a narrative progression, not measured milestones or a
reliable delivery schedule.

### Limitations acknowledged by the author

- Poor sources can contaminate several derived pages, making correction harder
  than removing a single stored document.
- Setup and early maintenance can feel slow before the collection is useful.
- The author claims that non-obvious connections become valuable around fifty
  to one hundred compiled sources; no supporting measurement is supplied.
- The workflow has tooling and model-running costs. Those costs depend on the
  chosen OpenAI or open-source deployment and its actual usage.

## 6. Critical assessment

| Claim or assumption | Assessment |
| --- | --- |
| Persistent synthesis can reduce repeated work | A sound design rationale, supported as a pattern by the original LLM Wiki proposal |
| Retrieval and compilation are alternatives | Overstated: retrieval can select compiled summaries, individual claims, and original sources together |
| Understanding is paid for only once | An approximation: new questions, corrections, and source changes still require reasoning and maintenance |
| The system inevitably gets smarter | Not guaranteed: useful knowledge can accumulate, but errors, duplication, and stale synthesis can accumulate too |
| Agents never forget links or contradictions | Too strong: comparison is limited by context, retrieval, model quality, and execution budgets |
| A source should update ten to fifteen pages | An illustrative workload, not a quality target |
| Fifty to one hundred sources establish a value threshold | Unsupported as a general threshold |
| Two weeks without an update means staleness | A possible review heuristic, not a validity rule |
| A connected graph demonstrates understanding | Insufficient: links need meaningful, evidence-backed relationships |
| Popularity demonstrates effectiveness | Insufficient: stars and views do not measure accuracy, recall, cost, or maintenance effort |

The two quotations attributed to Karpathy in the pasted article were not located
verbatim in the linked gist during the initial review. The first broadly matches
its argument. Their exact wording should remain unverified rather than being
repeated as confirmed quotations. The article's historical popularity figures
were not independently verified.

Additional engineering concerns are provenance, loss of qualifications during
summarisation, source retraction, incomplete conflict checks, and reusing an
agent's own output as if it were new evidence. Exact citations improve
auditability but do not independently prove the truth of a claim.

## 8. Candidate direction for Moon

The useful question is how Moon could maintain reusable cross-source
understanding while preserving its existing evidence and retrieval contracts.
The following are proposals for later evaluation, not implemented behaviour.

### A. Establish the baseline before adding another layer

Use the existing quality protocol to identify failures that persistent synthesis
would actually address: repeated cross-source reconstruction, incomplete topic
context, stale derived claims, or useful analysis disappearing between tasks.
Distinguish those from retrieval-ranking problems and missing source evidence.

Use a representative, sanitised corpus with explicit corrections, conflicting
sources, qualified claims, temporary facts, multilingual material, and unrelated
scopes. Compare against the existing Moon configuration rather than a hypothetical
raw-document-only baseline.

### B. Define provenance for broader source ingestion

If Moon accepts articles or other external documents into its learning workflow,
define the source type, identity, content revision or hash, publication and
observation times, scope, and exact supporting ranges. Preserve the difference
between the user's stated preference, an author's claim, and an agent inference.

An arbitrary reference document should not automatically be treated as a user
statement or as completed-session evidence. General ingestion support and its
learning eligibility need an explicit contract.

### C. Explore persistent topic synthesis

A candidate topic summary could have a stable scoped identity, a revision,
supporting claim and source references, unresolved disagreements, a synthesis
timestamp, and a dependency state. Supporting evidence and interpretation should
be distinguishable. Any Markdown page would be a generated view of canonical
database state.

This is a conceptual record shape, not a final schema. First test whether
existing memory records and exports can express the useful behaviour without
unnecessary new abstractions.

### D. Track dependencies and invalidate affected synthesis

When a supporting claim is corrected, expires, or loses valid support, derived
summaries should be identifiable and marked for review or recompilation. Source
removal and retraction need the same treatment. Updating a source must not leave
an apparently current summary silently relying on the old version.

Reprocess affected material within explicit budgets. Do not rewrite the whole
collection simply because another source arrived. Keep repeated processing
idempotent and apply related changes transactionally.

### E. Combine synthesis with existing retrieval

Context assembly could select an appropriate topic summary, precise active
claims, and their evidence within the existing packet budget. Clearly marked
reference excerpts remain useful when no adequate synthesis exists or when an
exact source detail is needed.

A summary should not crowd out more relevant evidence. Scope, validity,
supersession, deduplication, and citation rules must continue to apply.

### F. Make maintenance reviewable

A useful change brief would describe added or revised knowledge, affected topics,
unresolved disagreements, stale dependencies, and remaining unprocessed work.
It should distinguish completed work from deferred work and incomplete checks.
Private source content belongs in the authorised review surface; operational
metrics should retain Moon's content-free design.

## 9. OpenAI and open-source model use

The architecture should depend on explicit model capabilities and validated
outputs rather than one vendor's desktop product or instruction filename.

- Preserve Moon's existing separation between L1 extraction, L2 reconciliation,
  conversation models, and compaction models.
- Route work through the configured host/provider boundary. Do not introduce a
  second credential store or an implicit direct API-key path.
- Evaluate OpenAI and open-source candidates on grounded extraction, preserved
  uncertainty, citation correctness, structured output, latency, and cost.
- A smaller model may suit extraction and a stronger model may suit complex
  reconciliation; this is a hypothesis to measure, not an assumed allocation.
- Keep provider fallback explicit. A failed local request should not silently
  become a paid remote request.
- Preserve input, attempt, time, and action limits. Token settings should only be
  described as enforced limits when the selected backend actually enforces them.
- Model-generated knowledge remains untrusted context below owner instructions,
  regardless of which model produced it.

## 10. Candidate acceptance criteria

Any later implementation should demonstrate that:

1. Derived statements retain inspectable supporting evidence and qualifications;
   interpretations and disagreements remain distinguishable from established claims.
2. A repeated ingestion does not create duplicate claims, summaries, or links.
3. A correction or source retraction invalidates affected derived knowledge and
   does not leave stale content appearing current in normal recall.
4. Partial context or deferred processing is visible and is never presented as a
   complete conflict review.
5. Interrupted, failed, or concurrent processing preserves transactional storage
   and leaves work recoverable without losing evidence.
6. Existing lexical/hybrid recall and bounded context assembly continue to work;
   useful information is not displaced by redundant summaries.
7. Representative reviewed tasks show whether synthesis improves usefulness,
   grounding, and repeated research effort, alongside its latency and model cost.
8. The same evidence and lifecycle rules apply to OpenAI and open-source routes.
9. SQLite owns all persistent knowledge; Markdown is an optional import/export
   format, with no required knowledge files or synchronisation loop. Metrics do
   not acquire private queries, source text, or generated knowledge.

Page count, graph density, ingestion volume, and source-count milestones are not
substitutes for these outcomes.

## 12. Full SQLite knowledge storage

### Decision and scope

On 16 November 2026, the owner requested that Moon abandon Markdown files as a
knowledge-storage workflow and use SQLite completely. All durable knowledge,
including retained source content, claims, compiled topics, relationships,
revision history, review state, and processing progress, belongs in one canonical
SQLite database owned by the Rust binary.

Moon already stores canonical claims in SQLite. This extends that ownership to
the complete compiled-knowledge lifecycle; it does not imply that the current
runtime uses a Markdown vault as its canonical memory store.

There will be no required `raw/`, `wiki/`, `index.md`, `log.md`, or writable
Markdown memory tree. Agents interact through structured Moon commands, and
human-facing pages are rendered from database records. No Obsidian installation,
plugin, file watcher, graph server, or additional application runtime is required.

The following remain outside the knowledge-store decision:

- Repository instructions and documentation, including `AGENTS.md`, `SKILL.md`,
  `README.md`, and this MIP, retain their development and host-integration roles.
- Runtime configuration, binaries, model assets, and database backups remain
  operational files. SQLite WAL and shared-memory files belong to the same
  database; they are not separate knowledge stores.
- Provider credentials remain owned by the configured host/provider credential
  mechanism and must not enter knowledge tables, exports, or metrics.
- User-selected Markdown, text, and other supported files can be imported. Their
  captured database revisions become retained evidence; later filesystem edits
  do not silently change them.
- Markdown/JSON/HTML exports remain optional outputs. Normal learning, recall,
  maintenance, and review must work without generating any knowledge files.

### Records and ownership

The following defines logical records, not final SQL table names. Reuse existing
documents, memory revisions, citations, and learning jobs where their contracts
fit. Add numbered migrations only for capabilities existing records cannot
represent safely.

| Record | Required information and responsibility |
| --- | --- |
| Source identity | Stable ID, source kind, origin, scope, and learning eligibility |
| Source revision | Immutable sanitised captured content, content hash, publication time when known, observation/capture time, and extraction format/version |
| Claim revision | Stable scoped canonical identity, attributed statement, kind, evidence references, validity, uncertainty, and supersession state |
| Topic identity and revision | Stable scoped ID, title and aliases, maintained explanation, factual support, labelled inference, disagreements, open questions, and compilation state |
| Citation | Exact source-revision ID and byte/line or supported format-specific range that resolves against the retained revision |
| Relationship | Typed endpoints and meaning, with attribution or evidence when the relationship itself makes a factual claim |
| Dependency | Exact source/claim/topic revision consumed by a derived revision, input fingerprint, and invalidation state |
| Review and processing record | Proposed changes, reviewed disposition, expected input revisions, idempotency key, leases, attempts, applied changes, and deferred work |

Canonical prose can remain text in SQLite. Markdown syntax inside a text field
does not require a Markdown file. Indexes and presentation caches must be
rebuildable from retained canonical records; reviewed interpretation is not a
cache to discard and regenerate without history.

If a supported intake format needs an original binary attachment, retain its
bounded payload as a content-addressed BLOB in the same database, or explicitly
declare that format unsupported. Do not introduce an undocumented attachment
store. Establish size limits and backup implications before enabling large
binary ingestion; text-first intake is sufficient for the initial experiment.

### Source intake and provenance

Source capture must be explicit. Today's completed-turn recorder retains the
user request and final answer and omits intermediate tool traffic. An article
read during research therefore does not automatically become retained primary
evidence. The agent must submit its content and provenance separately before
Moon treats it as support for compiled external knowledge.

Intake should:

1. Classify material as a user statement, completed-session evidence, external
   author claim, reference, or generated analysis.
2. Sanitise before persistence, preserve that immutable representation, and
   locate citations against it.
3. Resolve a scoped source identity and create a revision only when retained
   content or material provenance changes. Matching content from different
   origins is not automatically independent corroboration or the same source.
4. Record learning eligibility explicitly. Importing text does not make it an
   owner instruction or approve every statement as a fact.
5. Queue bounded extraction/reconciliation work transactionally with intake.
   Model failure leaves captured evidence and recoverable pending work.

A URL alone is insufficient retained evidence because its content can change.
Publication time, capture time, and a claim's validity period are distinct.
Repeated intake of the same source revision must be idempotent. A revised source
does not overwrite its previous snapshot or citations.

### Claims, synthesis, and relationships

Preserve the conservative L1/L2 claim checks. Current L2 proposals cite selected
session evidence and ground non-review content against the newest cited evidence.
That contract cannot become general cross-source synthesis merely by changing a
prompt or treating every article as a completed user session.

Give derived synthesis its own contract. A topic revision records its exact input
revisions, associates factual statements with support, and labels interpretation.
It preserves competing claims and qualifications. Newer publication time or
repeated generated wording alone does not establish truth. Existing
`kind=summary` is not sufficient without these dependency and validity rules.

Start with relationships justified by workflows: `about`, `derived_from`,
`supersedes`, and an explicitly attributed disagreement relation. Add exploratory
related-topic links when useful. Navigation links do not count as evidence or
automatically create compilation dependencies. Backlinks are reverse queries,
not a second list that agents maintain.

Use stable IDs and scoped aliases, including multilingual aliases. Renaming a
topic must not break references; matching names across projects must not cause
automatic merging. Derivation dependencies reject cycles, while ordinary
conceptual relationships may be cyclic.

### Incremental compilation and freshness

Each compilation records its input revision fingerprint and compiler/prompt
version. Repeated processing with unchanged inputs is idempotent. A replacement
topic revision leaves the prior result auditable.

When a supporting claim or source is superseded, withdrawn, expires, or changes
eligibility, invalidate affected derived revisions and enqueue refresh work in
the same transaction where possible. Expiry also requires read-time checks so a
delayed maintenance tick cannot present expired support as current.

Invalidation propagates through dependent topics. Process affected work within
explicit budgets and report remaining backlog. Retrieval checks dependency
validity even while propagation or recompilation is incomplete. Stale synthesis
must be labelled or excluded, with current claims and source excerpts available
as fallback.

Compile from a bounded snapshot outside database write locks, then apply in a
short transaction with expected-revision checks. If an input changed while the
model was reasoning, reject or requeue the result. Leases, bounded retries, and
idempotency keys make concurrent or interrupted work recoverable.

### Agent and human workflows

```text
Explicit source intake -> attributed claims -> affected topic compilation
                      -> bounded recall -> useful work -> selective proposals
Corrections/retractions -> dependency invalidation -> bounded refresh
```

Moon owns validation and database mutations. Agents use versioned structured
command inputs and JSON responses to inspect knowledge, submit proposals,
review conflicts, and apply authorised changes. Raw SQL is not the normal agent
write interface. Command names and schemas require an interface review before
being advertised in `SKILL.md` or workflow documentation.

Reuse lexical and embedded-vector retrieval. Select fresh topic summaries
alongside precise active claims and original supporting excerpts, deduplicate
overlap, and preserve the existing packet budget. Bound the summary allocation
so it cannot crowd out more relevant evidence. Return explicit stale, disputed,
missing-support, and incomplete-review states. Do not load the entire graph into
every agent turn.

Useful query-time analysis may be proposed for retention with its dependencies
and inference labels. Its repetition is not independent confirmation. Owner
instructions remain separate from imported knowledge and generated synthesis.

Human views expose a topic's explanation, evidence, relationships, revision
changes, unresolved questions, and freshness. Corrections use Moon's revision
workflow; a rendered page is never a second writable truth. A visual graph is
optional. Source inspection and meaningful change review take priority, and
content-bearing review views stay separate from content-free metrics.

### Migration, portability, and delivery

Implementation should proceed in independently verifiable steps:

1. Establish a reviewed baseline with real cross-source questions. Compare
   prepared topic summaries with current Moon for grounding, repeated research
   effort, corrections, lost qualifications, and packet crowding.
2. Design source-revision citations and eligibility. Preserve session citations
   and claim revision identities; external sources must not weaken validation.
3. Add topic revisions, dependencies, invalidation, and bounded processing using
   numbered transactional migrations. Keep compilation disabled until isolated
   rehearsal demonstrates its lifecycle.
4. Add structured inspection/proposal/review operations and integrate fresh
   synthesis with recall. Align `SKILL.md`, `README.md`, and workflows with the
   actual implemented interface.
5. Add generated human views and optional portable exports. Remove required
   file-mediated knowledge steps only after their database paths are verified.
6. Deploy with separate approval, a consistent live database backup,
   configuration backup, and a tested restore path. Copying only a live SQLite
   main file while ignoring WAL state is not a consistent backup. Old binaries
   must not open newer schemas as a rollback strategy.

Existing generated memory exports are not a migration input by default: their
claims already exist in SQLite, and reimporting them risks duplication or
circular evidence. An explicitly selected legacy source can be imported once
with provenance. Legacy files and rollback bundles remain read-only; deleting
user files is a separate action, not a prerequisite for migration.

Portable exports should preserve stable IDs, source revisions, citations,
dependencies, lifecycle state, and schema version. A readable Markdown export
alone is not a full-fidelity backup. Verify database restoration and, if
implemented, structured export/import round trips in temporary homes.

Acceptance requires idempotent intake, exact citations, scope isolation,
revision-safe concurrency, crash recovery, transitive and time-based dependency
invalidation, and explicit handling of disagreement and generated analysis.
Benchmark retrieval on representative corpus sizes before claiming improvement.
Learning and recall must work with no generated Markdown files present and no
Obsidian or external database service installed.

This storage design is independent of model selection. OpenClaw can continue
serving L1/L2. A dedicated Codex login/backend remains a separate possible
extension, not a prerequisite for SQLite storage or for selecting
`openai/gpt-6.1-terra`.

### Implemented contract

- Version-1 structured JSON intake retains explicitly submitted UTF-8 text and
  bounded provenance. Source kinds distinguish external documents, user
  statements, references and generated analysis. Text and Markdown syntax are
  supported as stored text; neither requires a knowledge file.
- A source has a stable opaque ID and an exact `(scope, source_key)` identity.
  Its immutable revisions retain sanitised content, hashes, provenance,
  publication/capture times, eligibility and extraction version. SQLite guards
  reject identity/revision updates and deletions.
- Repeating the current sanitised representation returns the same revision.
  Changing content or material provenance requires the expected current revision
  ID. An immediate transaction serialises comparison and append, rejecting stale
  changing writes. Identical retries remain harmless even with a stale
  expectation. Returning deliberately to an older body creates a new revision.
- `source get`, `list`, `history` and `cite` inspect an existing database
  read-only. All require an exact scope. Pagination is bounded; citation offsets
  address the stored sanitised UTF-8 bytes, with derived quotations and line
  numbers. Old citations continue resolving after a later revision is captured.
- `health` reports source/revision counts and checks revision sequencing and
  content/provenance fingerprints. Online SQLite backup retains the complete
  source history. No required Markdown export or synchronisation step exists.

The command and error envelopes are versioned independently of database schema
9. See [source-storage.md](docs/source-storage.md) for the exact schema, commands,
limits, examples and trust contract. README, the agent skill, and workflow and
migration documentation describe the same implemented surface.

### Security decisions and explicit boundaries

The existing `ingest` path updates indexed documents and exposes them to recall.
Reusing it directly would lose immutable source snapshots and could expose
imported instructions during ordinary agent work. This milestone therefore
keeps captures in separate tables, outside search, context packets, embeddings,
completed-session evidence and current L1/L2.

Intake defaults to `reference_only`. A separate `--allow-learning` flag records
permission for future processing; embedded content cannot set it through JSON
fields. The flag does not approve a claim or run a compiler. Source outputs are
labelled as untrusted data. A caller-supplied author, kind or date is attribution,
not proof of authorship or authority.

Sanitisation precedes hashing and persistence of content and prose provenance.
Credential-shaped identities are rejected instead of being redacted into
colliding keys. Origin URLs accept only HTTP(S) without userinfo, query or
fragment; signed and query-bearing URLs need a safe canonical origin or must be
omitted. No origin or embedded path is fetched. Actual input reads are bounded,
file inputs must be regular files, and final symlinks are rejected on Unix.
Parser errors and arbitrary SQLite trigger errors do not echo submitted data.

Two limits are fundamental: pattern-based sanitisation cannot identify every
secret, and scopes are logical separation rather than an ACL against the local
database owner. Existing owner-only file permissions remain necessary. SQLite
and its backups contain retained plaintext; this milestone adds no encryption
at rest. Imports must be selected deliberately and exclude authentication files
and unnecessary private content.

Before automatic source processing, complete the general-source claim/citation
contract, transactional job scheduling, withdrawal/eligibility invalidation and

produces read-only citation descriptors; it does not attach them to validated
claims. Topic compilation, dependency propagation, recall integration, binary
attachments and generated
human views remain later milestones. A representative reviewed quality baseline
is still required before claiming synthesis or retrieval improvements.

## 15. Approved durability and source lifecycle follow-up

Approved on 16 November 2026. This section separates the implemented durability
change from lifecycle requirements for the upcoming source-learning milestone.

### FULL durability: implemented in the checkout

Every writable Moon store connection now explicitly sets
`PRAGMA synchronous = FULL` alongside WAL mode. This covers new databases,
migrations, additional writers and reopening. Backup destination connections
also explicitly request `FULL`. The setting is connection-local, so it must be
applied on each writer rather than treated as a persisted database preference.

SQLite FULL requests a WAL sync at each commit before acknowledging success,
closing the recent-commit power-loss risk associated with NORMAL. This depends
on the operating system and storage honouring sync requests; it is not a
replacement for backups. Additional commit latency is possible; no performance
improvement is claimed.

A regression test inspects the actual Moon writer connection on creation,
after a committed write, on a second simultaneous writer and after reopening.
It asserts `synchronous=2` (FULL) and `journal_mode=wal`, checks visibility of the
committed state and verifies database health. Querying a separate inspection
connection would not prove the writer's setting.

### Minimal source lifecycle policy: approved for implementation

1. **Retain history by default.** Keep source revisions and citations without
   automatic age-based deletion. Staleness affects eligibility for use, not
   retention of supporting evidence.
2. **Withdraw without erasing evidence.** Stop learning and normal recall from
   withdrawn sources immediately, including application of in-flight results.
   Invalidate their support for dependent claims and topics, retaining reasons
   and history. Exclude unsupported derivations; revalidate claims with other
   independent valid support. Reimport must not silently reactivate a source.
3. **Preview explicit deletion.** Show affected source records, citations,
   claims and topics before authorisation. Reject stale plans, apply only the
   authorised scope, and reconcile support atomically with deletion. Unsupported
   derivations must become unusable immediately; independently supported claims
   may remain after revalidation. Do not silently delete unrelated sources.
   Logical deletion does not guarantee secure physical byte erasure. Existing
   backups and filesystem snapshots are separate retained copies; deleting from
   the working database does not remove them.
4. **Recover interrupted work.** Once automatic source processing is enabled,
   capture and required job creation must be transactional. Jobs need idempotency
   keys, expiring leases, bounded retries and inspectable failure states. Recheck
   source revision and eligibility before applying results, and commit results
   with job completion atomically. Preserve evidence after failures.

Current source storage provides retained immutable revisions and inspection.
Withdrawal, deletion planning/application, general-source claim linkage and
source-processing jobs still require implementation and validation. Automatic
source learning must remain disabled until those requirements are met. Policy
approval does not authorise deletion of existing data. The operational contract
is mirrored in [source storage](docs/source-storage.md#approved-lifecycle-policy).

## 17. Second milestone: reviewed source learning and recoverable jobs

Implemented in the checkout on 16 November 2026 following approval of the next
milestone. Numbered transactional migration `0010_source_learning.sql` adds
source lifecycle and event history, extraction jobs, accepted source statements
and exact support records. It backfills pending work for existing eligible

The installed local runtime was subsequently migrated to schema 10 after the
separately authorised backup, rehearsal and deployment recorded in §18.

### Source-to-statement contract

Eligible capture and required job creation commit together. Repeated capture
does not duplicate jobs. An explicit `source learning prepare` leases a bounded
complete-source snapshot; the host proposes at most 16 verbatim quotations.
Unknown actions and fields, invented quotations, invalid UTF-8 ranges and
ambiguous occurrences without an exact offset are rejected. No source body is
silently truncated. Oversized jobs remain inspectable and do not block fitting
jobs for other source keys.

`source learning submit` retains proposals outside recall. Acceptance requires
the exact reviewed result hash and explicit caller-side confirmation; the model
cannot request acceptance in its JSON. Rust rechecks the current revision,
eligibility, lifecycle generation and complete quotations before atomically
committing statements, support, indexes and the completed job. Repeated
acceptance is idempotent. Rejection retains a reviewed disposition without
indexing the proposals.

Accepted statements are separate from `memory_items` and `evidence_sessions`.
They use a reserved `source_claim` document kind and URI namespace, protected
from ordinary ingest. A caller-supplied user-statement kind remains attribution,
not authentication or an owner instruction. Author, user and generated statement
classes remain distinct; citations retain each source's original provenance.

For this initial contract, each independent support must quote the entire
unchanged statement. Identical text in the same scope and attribution class can
share support; repeated or copied sources do not increase a truth/confidence
score. Broader paraphrasing, inferred statements, and combinations where several
partial sources jointly support one conclusion remain later work. Exact bytes
do not prove that a selected excerpt preserves all context or qualifications;
review must inspect the surrounding source before accepting it.

### Lifecycle policy implemented

- Retain source revisions, accepted statement history and lifecycle reasons by
  default. No automatic age-based deletion was introduced.
- Withdrawal checks both expected revision and lifecycle generation, stops
  source learning, cancels incomplete jobs and reviews, and invalidates support
  immediately. Unsupported claims are removed from active indexes and embedding
  work atomically. Independently supported statements remain available.
- Source changes and eligibility changes invalidate prior-head support and
  fence late results. Reimport does not silently clear withdrawal.
- Explicit restoration records its reason and a new generation. Only previously
  accepted support that is still current and eligible can reactivate; new
  extraction proposals still require review.
- Deletion preview fingerprints source revisions, dependent claims and all their
  supports, jobs and lifecycle history. Apply rejects changed plans, removes the
  selected source content and copied pending proposals, reconciles support and
  removes unsupported derived records in one transaction. Statements with other
  valid support remain retained, even if expired and excluded from recall.
  Source identity and a deletion event remain as a tombstone; ordinary import
  cannot recreate that scoped identity. Logical deletion does not erase prior
  backups, filesystem/WAL bytes, or text already disclosed to a model/host.

Validity checks apply before lexical candidate limits and vector KNN selection,
through context assembly, and during embedding selection/application and index
rebuilding. Expiry is checked at read time without waiting for a maintenance
tick. Source statements render as untrusted, attributed references. Each
retrieved chunk is mapped back to the matching original-source byte/line range;
packet trimming keeps displayed statements and source quotes aligned.

### Recoverable processing and configured model execution

Jobs have queued, leased, review, complete, dead and cancelled states. Preparation
claims one job transactionally. Attempts use fresh ownership tokens, bounded
lease durations and at most three attempts before dead state; failures persist
only allowlisted codes. Expired leases recover on the next preparation.
Explicit retry can restart current queued/dead work, but cannot revive cancelled
or obsolete snapshots. Model work runs outside database write transactions.

The optional OpenClaw `moon_source_learn` tool processes one queued source using
the enabled configured L1 model, reasoning, fallback and timeout. Its 64 KiB
source-body limit bounds this first host integration. It requires trusted owner
and current-invocation authority, an explicit Moon home, and rechecks authority
before each primary/fallback attempt and before submission/disclosure. Model
tools are disabled. Failures and cancellation release only the fenced attempt
with bounded cleanup; expired leases remain recoverable.

The tool returns a pending-review job and result hash. It cannot accept claims,
change eligibility, withdraw or delete sources. There is no automatic source
processing timer, and existing completed-session L1/L2 semantics are preserved.
Source-facing CLI, README, skill, workflow and architecture documentation match
these implemented boundaries.

### Implemented behaviour and review findings

- Reference selection is separate from personal-memory/correction matching.
  Bounded term weighting and query-clause balancing allow evidence to support

  qualifications. Whole-question topic retrieval order is retained as a distinct
  signal from individual-source ranking.
- Collection names can establish only their own scope context. Other named
  subjects must match the admitting clause's evidence/title. Explicit-name
  comparison fragments require a second topical match; generic one-word

  before stemming, avoiding the discovered `does` → `doe` false-name anchor.

  premises each, with at most two topics. Every lookup checks the accepted claim,

  grant source prose authority or promote interpretation into personal facts.
- Selected source evidence is packed before topic explanations. Accepted source
  statements now remain complete or are omitted, including statements whose

## 22. Future milestone: working memory and detailed recall

Proposed on 16 November 2026 following the packet comparison. The user proposes
concise, fast near-term recall for ordinary requests, with older detailed
knowledge consulted for particular situations or explicit needs. Daily L2
distillation should maintain the concise layer. This section records future
design work only; it does not change today's implementation or deployment scope.

The user agreed to this direction: working memory is selected by activity,
importance and age; daily L2 maintains concise cited summaries; new L1 facts
and corrections remain immediately available; withdrawal invalidates dependent
summaries promptly. Record this as an agreed future design, not an implemented
feature. Current retrieval profiling and optimisation take priority.

### Purpose and relationship to packet size

Stored collection size determines the available search space; packet size caps
what is delivered to the agent. These are separate controls, although retrieval,
packing and model-input costs can interact. Section 21's benchmark found little
tail-latency difference between packet budgets but substantial cost growth from
1k to 10k stored references. The proposed layers aim to bound ordinary retrieval
work as the full collection grows. They do not establish a measured speed gain
yet, and the assumption that most requests need only recent context must be
validated against representative tasks.

### Two logical layers in the existing SQLite database

- **Working memory:** a bounded, indexed set of recent accepted facts, current
  goals, active project state, unresolved decisions and concise cited summaries.
  Selection considers relevance, activity, importance, explicit pins and
  recency. Age alone must not hide an enduring preference, active commitment or
  important correction. Personal facts and attributed source interpretations
  retain their separate types and authority boundaries.
- **Detailed memory:** retained original sources, exact accepted claims,
  revisions and topic history, including recent material too detailed for the
  working set. It remains the authoritative evidence behind both layers.
  Moving an item out of the working set removes derived membership only; it
  does not delete the source or alter its retention policy.

Keep one Rust binary and one SQLite database. The working layer is a rebuildable
projection with stable links to its exact evidence, not a second authoritative
store. Its item and character budgets must be bounded per scope. A small result
limit alone is insufficient: indexes and query plans must restrict the candidate
set before expensive joins, ranking and evidence loading. The normal fast path
must not silently perform full-history search on every request.

### Recall routing

1. Search the relevant working set first for ordinary current-work questions.
   Select a concise packet within the independently configured packet budget.
2. Access detailed memory directly for explicit history, dates, original quotes,
   past decisions or a named older project. Also allow bounded fallback when
   the working set has no adequate support, contains conflicting evidence or
   cannot cover the requested detail. Do not rely only on an LLM's self-reported
   confidence to decide whether evidence is sufficient.
3. Retrieve only relevant detailed evidence, preserving scope, attribution and
   qualifications. Reactivated project facts can become candidates for working
   memory; a retrieval alone must not count as independent confirmation or make
   an old observation newly true. Expose whether detailed recall was attempted
   so a working-set miss is not reported as proof that Moon has no such memory.

### Daily L2 maintenance, with immediate correctness

Extend daily L2 with a separate bounded maintenance job for the working layer:
reconcile changed accepted facts, propose concise cited summaries, prioritise
active material and remove obsolete derived memberships. Reuse the existing
model route and recoverable-job conventions, including leases, bounded retries,
idempotency, input revision checks and atomic publication. Avoid rereading the
entire archive each night; process changes plus a bounded rotation for ageing
and reactivated projects. Capacity must reserve room for fresh evidence so old
pinned summaries cannot permanently occupy every slot.

Existing daily session L2 reconciles session evidence; it does not currently
perform this maintenance or automatically compile source topics. Reusing its
route must not bypass the separate review requirements for source/topic
interpretations. Lossy summaries preserve uncertainty, negation, disagreement
and evidence links; they cannot silently replace canonical claims or discard
the originals.

New accepted L1 memories need an immediate bounded route into recall, without
waiting for the daily job. Corrections, expiry, withdrawal, scope changes and
purges must invalidate affected working entries and summaries as part of the
existing lifecycle, including transitive dependencies. At publication, reject
stale L2 snapshots. If maintenance fails or is disabled, keep only still-valid
previous entries and allow bounded detailed fallback; never serve withdrawn
evidence because its summary has not been rebuilt. Prompt/source content must
not acquire authority to change recall policy or access another scope.

### Validation and decisions before implementation

Compare the current retrieval path with the proposed working-first path using
the same packet cap and fixed working-set size while growing detailed storage
through 1k, 10k and, if practical, 100k references. Measure fast-path and detailed
fallback latency separately, fallback frequency, complete-evidence coverage and
false positives. Use the existing 50 ms warm p95 target for ordinary recall;
agree a separate bounded target for detailed recall before implementation.
Do not average rare slow history queries into fast-path claims or claim a
speedup merely because older correct answers have become inaccessible.

Regression cases must include an old but active preference, a new correction to
an old fact, explicit historical recall, returning to an inactive project,
multiple scopes, mixed languages, final qualifications, withdrawn support,
maintenance failure and restart recovery. Validate real L2 summaries separately
from deterministic retrieval, including whether compression changes meaning.
Operational measurements should remain content-free; do not add raw prompts or
retrieved private text to ordinary telemetry.

Open decisions are working-set budgets, promotion/ageing rules, fallback
criteria, summary review boundaries and the detailed-recall latency target.
Current query profiling and optimisation remain separate work before deployment;
this future architecture must not substitute for fixing expensive validity
queries used by either layer. No runtime, schema, scheduler, model configuration
or live data was changed when recording this proposal.

## 23. Retrieval profiling and optimisation before deployment

### Confirmed cause and focused changes

Profiling with Moon's bundled SQLite 3.51.3 found that joined uses of
`source_valid_claims` repeatedly materialised and deduplicated the complete
valid-claim set. At 10k references, source-context identity lookup scanned
2,002 supports and executed 124,223 VM operations for one requested claim.
Loading many candidate references multiplied that cost. Direct document-ID
lookups were already indexed; the problem was repeated work in joined callers.

Numbered transactional migration 12 replaces the view's `DISTINCT` support join
with a correlated `EXISTS`. Claim/document uniqueness preserves one result row
per claim. The same lookup now executes 91 VM operations with no full scan.
Read-time expiry, latest source revision, scope, eligibility and withdrawal
checks remain intact. No original source, claim, citation, identifier or topic
dependency is rewritten, and migrations 10 and 11 remain unchanged.

took about 0.0035 ms to execute but 0.171 ms to prepare and execute per candidate.

parameters and live validity are checked on every execution. Ranking, packet
contents, original evidence and lifecycle semantics are unchanged.
